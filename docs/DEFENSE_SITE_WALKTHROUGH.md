## I. Вступление (2–3 минуты)

> Уважаемый председатель, уважаемые члены государственной аттестационной комиссии!
>
> Тема нашей дипломной работы — **разработка веб-платформы ParkPass** для агрегированного бронирования билетов в тематические парки развлечений.
>
> **Актуальность.** Сегодня турист, желающий посетить, например, зону Star Wars или Harry Potter, вынужден искать информацию на разных сайтах: официальный сайт парка, агрегаторы, отзывы, сравнение тарифов. Это отнимает время и создаёт риск переплаты. ParkPass решает эту проблему: **один интерфейс** — каталог парков, сравнение цен, бронирование, электронный билет с QR-кодом, личный кабинет, программа лояльности и административное управление.
>
> **Цель работы** — спроектировать и реализовать full-stack веб-приложение с клиент-серверной архитектурой, REST API и реляционной базой данных PostgreSQL.
>
> **Задачи:**
> 1. Разработать серверную часть (REST API, аутентификация, бизнес-логика).
> 2. Спроектировать схему базы данных и механизм наполнения демо-данными.
> 3. Реализовать клиентскую часть с тематическими страницами четырёх вселенных.
> 4. Внедрить многошаговое оформление заказа и электронные билеты с QR-кодом.
> 5. Создать административную панель: модерация, управление парками, проверка билетов на входе.
> 6. Обеспечить автоматизированное тестирование backend.
>
> **Результат** — работающий прототип, который мы сейчас подробно разберём по каждому экрану и каждому модулю системы.

## II. Общая архитектура — как всё связано (2 минуты)

> Прежде чем идти по страницам сайта, покажу **скелет системы**.
>
> ParkPass — это **трёхзвенная архитектура**:
>
> ```
> Браузер (Next.js 14)  →  REST API (Express + TypeScript)  →  PostgreSQL 16
> ```
>
> **Frontend** — то, что видит пользователь: страницы, кнопки, формы. Он **не обращается к базе данных напрямую**. Все данные приходят через HTTP-запросы к API на порту 4000.
>
> **Backend** — сервер приложений. Он проверяет права доступа (JWT-токен), выполняет бизнес-правила (можно ли забронировать, действителен ли билет) и читает/записывает данные.
>
> **База данных** — семь таблиц: пользователи, парки, аттракционы, типы билетов, бронирования, отзывы, избранное.
>
> **Важная инженерная особенность — dual-mode.** Если PostgreSQL доступна (через Docker), данные сохраняются постоянно. Если нет — backend автоматически переходит в **mock-режим**: данные в оперативной памяти. Это позволяет разрабатывать frontend и гонять 13 автотестов без Docker. Бизнес-логика при этом **одна и та же** — сервисы выбирают хранилище через функцию `dbIsReady()`.
>
> Проверить режим можно запросом `GET /health` — в ответе поле `"database": "postgresql"` или `"mock"`.

## III. Backend — что происходит «под капотом» (4–5 минут)

### 3.1. Структура серверного кода

> Код backend организован по принципу **разделения ответственности**:
>
> | Слой | Папка | Задача |
> |------|-------|--------|
> | Маршруты | `routes/` | Принять HTTP-запрос, вернуть код ответа |
> | Middleware | `middleware/auth.ts` | Проверить JWT и роль пользователя |
> | Сервисы | `services/` | Бизнес-логика: бронь, отзывы, парки |
> | Данные | `db/` + `data/catalog.ts` | PostgreSQL или in-memory |
>
> Поток запроса: **HTTP → Route → Middleware → Service → БД → JSON-ответ**.

### 3.2. Аутентификация и роли

> **Регистрация и вход** (`POST /api/v1/auth/register`, `POST /api/v1/auth/login`):
> - Пароль **никогда не хранится в открытом виде** — только bcrypt-хеш (cost factor 10).
> - При успешном входе сервер выдаёт **JWT-токен** сроком 7 дней.
> - Frontend сохраняет токен в `localStorage` и отправляет в заголовке `Authorization: Bearer <token>`.
>
> **Три роли (RBAC — Role-Based Access Control):**
>
> | Роль | Что может |
> |------|-----------|
> | `user` | Бронировать, избранное, отзывы, личный кабинет |
> | `park_manager` | Всё выше + админ-статистика, брони, модерация отзывов, проверка QR, редактирование парков |
> | `admin` | Всё выше + управление ролями пользователей |
>
> Middleware `requireRole('admin', 'park_manager')` блокирует доступ обычному пользователю к `/api/v1/admin/*` с кодом **403 Forbidden**.

### 3.3. Основные API-модули

> **Парки** — `GET /api/v1/parks` с фильтрами по категории, городу, дате. Для каждого парка: аттракционы, типы билетов, расписание на 7 дней, проверка доступности слотов (лимит 500 гостей в день).
>
> **Бронирования** — `POST /api/v1/bookings` создаёт заказ. Сервер генерирует уникальный код `PP-{timestamp}` и сохраняет бронь со статусом `paid`. Начисляются баллы лояльности (1 балл за каждый евро). `GET /api/v1/bookings/me` — история заказов текущего пользователя.
>
> **Отзывы** — публичный `GET` возвращает только одобренные (`is_approved = true`). Новый отзыв создаётся с `is_approved = false` и ждёт модерации.
>
> **Избранное** — привязка парка к пользователю в таблице `favorites`.
>
> **Админ** — статистика, управление бронями, модерация отзывов, редактирование каталога парков, **проверка и check-in билетов по QR**.

### 3.4. Тестирование

> Файл `backend/src/__tests__/api.test.ts` содержит **13 интеграционных тестов**: health check, каталог парков, расписание, бронирования, отзывы, RBAC (user получает 403 на админку, admin — 200). Запуск: `cd backend && npm test`.

### 4.2. Главная страница `/`

> **Файл:** `frontend/src/app/page.tsx` · **Тип:** Server Component (данные грузятся на сервере при открытии страницы)

> - Справа — коллаж из изображений (компонент `next/image` — оптимизация, lazy load).
>
> **Блок доверия (три карточки):**
> - «Прозрачная цена» — итоговая сумма без скрытых сборов.
> - «Мгновенное подтверждение» — QR-билет сразу после оплаты.
> - «Кэшбэк до 12%» — программа лояльности ParkPass Club.

> **Как это работает (3 шага):** выбрать парк → забронировать → получить QR.

> **Если backend не запущен:** страница **не падает**. Функция `safeFetch()` перехватывает ошибку сети, показывается подсказка «Запустите backend на порту 4000». Это называется **graceful degradation**.

### 4.6. Авторизация `/auth`

> **Файл:** `frontend/src/app/auth/page.tsx` · **Тип:** Client Component
>
> - Две вкладки: **Вход** и **Регистрация**.
> - Форма отправляет `POST /api/v1/auth/login` или `register`.
> - При успехе: `saveSession(token, user)` в `localStorage`, редирект на страницу из параметра `?next=`.

> Демо-данные уже подставлены в форму для быстрой демонстрации на защите.

### 4.8. Личный кабинет `/account`

> **Файл:** `frontend/src/app/account/page.tsx`
>

>

>

>
> **История бронирований:** `GET /api/v1/bookings/me`. Для каждой активной брони отображается компонент **BookingQrCard**:

> - текстовый код `PP-...`;
> - парк, дата, гости, сумма;
> - подсказка: «Покажите QR на входе».
>
> QR кодирует JSON: тип `parkpass-ticket`, код, парк, дата, число гостей — чтобы контролёр мог и отсканировать, и проверить вручную.

## V. Оформление заказа (Checkout) — полный цикл (3 минуты)

> **Компоненты:** `CheckoutWizard`, `HarryPotterCheckoutWizard`, `MarvelCheckoutWizard`, `JurassicCheckoutWizard`  
> **Общая логика:** `lib/checkout-api.ts` → функция `confirmCheckoutBooking`
>
> **Три шага визарда:**
>
> | Шаг | Название | Что делает пользователь |
> |-----|----------|-------------------------|
> | 1 | Гость | Выбор типа билета, даты визита, числа гостей (до 12), ввод email и имени |
> | 2 | Оплата | Демо-форма карты (MVP — без реального платёжного шлюза) |
> | 3 | Подтверждение | Итоговая сумма, кнопка «Оплатить» |
>
> **Что происходит при нажатии «Оплатить»:**
> 1. Проверяется JWT — нет токена → редирект на `/auth?next=...`.
> 2. `POST /api/v1/bookings` с телом: parkSlug, ticketId, visitDate, guests, totalAmount.
> 3. Backend создаёт бронь, генерирует `qrCode`, начисляет баллы.
> 4. Frontend показывает **экран успеха** с `BookingQrCard` — QR и код.
> 5. Тот же билет доступен в `/account`.
>
> **Визуально** каждая вселенная имеет свой checkout (цвета, шрифты, фон), но **бизнес-логика одна** — это правильное разделение presentation и application layer.

## VI. Административная панель `/admin` (3–4 минуты)

> **Файл:** `frontend/src/app/admin/page.tsx` → компонент `AdminDashboard`  
> **API:** `lib/admin-api.ts` → префикс `/api/v1/admin`
>
> Доступ только для ролей `admin` и `park_manager`. Обычный user увидит ошибку «Недостаточно прав».

### Вкладка «Обзор»

> KPI-карточки: всего бронирований, выручка в евро, число пользователей, число парков.  
> Таблица «По паркам» — сколько броней и выручка на каждый парк.  
> «Последние бронирования» — быстрый мониторинг.  
> Данные: `GET /api/v1/admin/stats`.

### Вкладка «Бронирования»

> Полная таблица заказов: парк, дата, гости, сумма, **QR-код**, статус.  
> Выпадающий список меняет статус: `pending` → `paid` → `completed` → `cancelled`.  
> Запрос: `PATCH /api/v1/admin/bookings/:id/status`.

### Вкладка «Проверка билета» *(контроль на входе в парк)*

> Это имитация работы контролёра на турникете.
>
> 1. Гость показывает QR с телефона (из checkout или личного кабинета).
> 2. Контролёр вставляет код `PP-...` или JSON из QR в текстовое поле.
> 3. **«Проверить»** — `POST /api/v1/admin/bookings/verify` с `{ qrCode }`.  
>    Сервер проверяет: билет существует, не отменён, не использован, статус paid/pending, **дата визита = сегодня**.
> 4. **«Отметить вход»** — тот же запрос с `{ checkIn: true }`. Статус брони → `completed` («билет погашен»).
>
> На защите: забронируйте с **сегодняшней датой**, затем проверьте код в админке.

### Вкладка «Парки» *(управление каталогом)*

> Список всех парков. При раскрытии — форма редактирования:
> - название, описание, цена «от», URL обложки, бейдж;
> - таблица типов билетов: название и цена каждого тарифа.
>
> Сохранение: `PATCH /api/v1/admin/parks/:slug` и `PATCH .../tickets/:ticketCode`.  
> В mock-режиме изменения хранятся в памяти (`catalog-overrides.ts`); в PostgreSQL — пишутся в БД.

### Вкладка «Отзывы» *(модерация)*

> Фильтры: все / на модерации / опубликованные.  
> Для каждого отзыва: опубликовать или скрыть, пометить «проверенным», удалить.

## VII. QR-код и безопасность билета (2 минуты)

> **Генерация:** при `POST /bookings` backend создаёт код формата `PP-{timestamp в base36}`.
>
> **Содержимое QR** (frontend, `lib/booking-qr.ts`):
> ```json
> {
>   "type": "parkpass-ticket",
>   "v": 1,
>   "code": "PP-XXXX",
>   "park": "star-wars-galaxys-edge",
>   "parkName": "Star Wars: Galaxy's Edge",
>   "date": "2026-06-17",
>   "guests": 2,
>   "ticket": "Premium"
> }
> ```
>
> **Проверка на входе** — только через backend, не на клиенте. Нельзя подделать билет изменением JSON в браузере: сервер сверяет код с записью в `bookings`.
>
> **Причины отказа:** билет не найден, отменён, уже использован (completed), неверная дата, недопустимый статус.

## X. Шпаргалка: частые вопросы комиссии

**Почему Next.js, а не чистый React?**  
SSR и Server Components — данные в HTML с первого запроса, лучше SEO для лендингов парков.

**Почему Express, а не NestJS?**  
Прозрачная архитектура без «магии» фреймворка — для диплома важно показать понимание HTTP-слоя.

**Безопасно ли JWT в localStorage?**  
Для MVP и диплома — да, с CORS-ограничением. В production рекомендуется httpOnly cookie.

**Что если backend упал?**  
`safeFetch()` — сайт не крашится, показывает пустые списки и подсказку.

**Как отличить ваш проект от Booking.com?**  
Фокус на тематических парках с иммерсивным брендированным UX, а не универсальный агрегатор отелей.

**Использовали ли AI?**  
Да, как инструмент ускорения (Cursor). Архитектура, логика, дизайн вселенных и демонстрация — наши. Код проверен тестами и вручную.
