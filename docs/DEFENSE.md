## 2. Backend — полное пояснение

### 2.1. Назначение серверной части

Backend ParkPass — это **сервер приложений**, который:
- хранит и отдаёт данные о парках, билетах, аттракционах;
- обрабатывает регистрацию, вход и авторизацию пользователей;
- создаёт и ведёт бронирования с QR-кодами;
- управляет избранным и отзывами;
- предоставляет администраторам статистику, отчёты и инструменты модерации.

Клиент (браузер) **не имеет прямого доступа к базе данных** — все операции проходят через REST API. Это классическая **трёхзвенная архитектура**: Presentation (frontend) → Application (backend) → Data (PostgreSQL).

### 2.2. Технологический стек

| Компонент | Технология | Зачем выбрана |
|-----------|------------|---------------|
| Runtime | Node.js 20 | Единый язык с frontend (TypeScript), высокая скорость разработки |
| Framework | Express 4 | Минималистичный, гибкий, стандарт де-факто для Node.js REST API |
| Язык | TypeScript 5 | Статическая типизация, меньше ошибок в runtime, удобство рефакторинга |
| БД | PostgreSQL 16 | Надёжная реляционная СУБД, JSONB для тематики парков, ENUM-типы |
| Аутентификация | JWT (jsonwebtoken) | Stateless-токены, не нужны серверные сессии |
| Пароли | bcryptjs | Одностороннее хеширование, защита от утечки паролей |
| Тесты | Jest + Supertest | Интеграционное тестирование HTTP-эндпоинтов |
| Dev | ts-node-dev | Hot reload при разработке |

### 2.3. Архитектура кода

```
HTTP-запрос
    ↓
Routes (маршруты)     — парсинг запроса, HTTP-коды ответа
    ↓
Middleware (auth.ts)  — проверка JWT, проверка роли (RBAC)
    ↓
Services (сервисы)    — бизнес-логика
    ↓
PostgreSQL / Mock     — хранение данных
```

**Папки `backend/src/`:**

| Папка / файл | Назначение |
|--------------|------------|
| `main.ts` | Точка входа: подключение к БД, seed, запуск сервера на порту 4000 |
| `app.ts` | Создание Express-приложения (используется и в тестах) |
| `routes/` | HTTP-маршруты: auth, parks, bookings, favorites, reviews, admin |
| `services/` | Бизнес-логика каждого домена |
| `middleware/auth.ts` | JWT: `requireAuth`, `optionalAuth`, `requireRole` |
| `data/catalog.ts` | Единый каталог 4 парков — источник данных для seed и mock |
| `db/pool.ts`, `db/seed.ts` | Подключение к PostgreSQL и автозаполнение |
| `mappers/park.mapper.ts` | Преобразование строк БД в API-формат |
| `types.ts` | TypeScript-интерфейсы DTO |
| `__tests__/api.test.ts` | 13 интеграционных тестов |

### 2.4. Ключевое решение: dual-mode (PostgreSQL + Mock)

Сервер работает в **двух режимах**:

1. **PostgreSQL** — если задан `DATABASE_URL` и БД доступна. Данные персистентны, подходит для демонстрации на защите.
2. **In-memory Mock** — если БД недоступна. Данные в оперативной памяти, удобно для разработки и CI без Docker.

Переключение прозрачно: каждый сервис проверяет `dbIsReady()` и выбирает реализацию. Эндпоинт `GET /health` возвращает `"database": "postgresql"` или `"mock"`.

**Почему это важно для диплома:** показывает понимание **отказоустойчивости** и **разделения слоёв** — бизнес-логика не зависит от конкретного хранилища.

### 2.5. База данных

**Схема** (`database/schema.sql`) — 7 таблиц:

| Таблица | Что хранит |
|---------|------------|
| `users` | Пользователи: email, хеш пароля, роль, клубный уровень, баллы лояльности |
| `parks` | Парки: название, slug, город, рейтинг, тема (JSONB), часы работы |
| `attractions` | Аттракционы парка |
| `ticket_types` | Типы билетов и цены |
| `bookings` | Бронирования: дата визита, гости, сумма, статус, QR-код |
| `reviews` | Отзывы: рейтинг, текст, флаги `is_approved`, `is_verified` |
| `favorites` | Избранные парки пользователя |

**ENUM-типы:** `user_role` (user, park_manager, admin), `booking_status` (pending, paid, cancelled, completed), `club_tier` (bronze, silver, gold, platinum).

**Индексы** по часто используемым полям: `city`, `category`, `rating`, `park_id`, `user_id`, `visit_date`.

### 2.6. Аутентификация и безопасность

**Поток регистрации:**
```
POST /api/v1/auth/register
  → валидация email/пароля
  → bcrypt.hash(password, 10)
  → INSERT в users (роль: user)
  → JWT { sub: userId, email }, срок 7 дней
  → ответ: { token, user }
```

**Поток входа:**
```
POST /api/v1/auth/login
  → поиск пользователя по email
  → bcrypt.compare(password, hash)
  → JWT
```

**Защита эндпоинтов:**
- `requireAuth` — обязательный заголовок `Authorization: Bearer <token>`
- `requireRole('admin', 'park_manager')` — проверка роли из БД

**Роли (RBAC):**

| Роль | Права |
|------|-------|
| `user` | Бронирования, избранное, отзывы, профиль |
| `park_manager` | + админ-статистика, брони, отчёты, модерация отзывов |
| `admin` | + управление пользователями и их ролями |

### 2.7. Основные модули API

#### Парки (`/api/v1/parks`)
- Список с фильтрами: город, категория, рейтинг, цена
- Детали парка по slug
- Аттракционы, типы билетов
- Расписание на 7 дней
- Проверка доступности слотов (capacity 500 гостей/день)

#### Бронирования (`/api/v1/bookings`)
- `GET /me` — история броней авторизованного пользователя
- `POST /` — создание: parkSlug, ticketId, visitDate, guests, totalAmount
- Генерация QR: `PP-{timestamp}`
- Статус сразу `paid` (упрощённая оплата для MVP)
- Начисление баллов лояльности = floor(сумма)

#### Отзывы (`/api/v1/reviews`)
- `GET ?parkSlug=` — только одобренные (`is_approved = true`)
- `POST` — новый отзыв с `is_approved = false` → **модерация**
- При изменении отзыва пересчитывается `rating_avg` парка

#### Админ (`/api/v1/admin`)
- Статистика: пользователи, парки, брони, выручка
- Управление статусами бронирований
- Модерация отзывов: одобрить, скрыть, верифицировать, удалить
- Управление ролями пользователей (только admin)
- Отчёты: бронирования по периоду, посетители по датам

**Всего: 30 эндпоинтов** (включая health check).

### 2.8. Тестирование backend

Файл `backend/src/__tests__/api.test.ts` — **13 тестов** в mock-режиме:

- Health check
- Список 4 парков

Запуск: `cd backend && npm test`

>
> Мы реализовали полный цикл работы платформы: от каталога парков до бронирования с QR-кодом и модерации пользовательского контента. Особое внимание уделено безопасности — пароли хешируются через bcrypt, доступ к административным функциям защищён ролевой моделью RBAC.

## 3. Frontend — полное пояснение

### 3.1. Назначение клиентской части

Frontend ParkPass — это **пользовательский интерфейс**, через который посетитель:
- ищет и сравнивает тематические парки;
- изучает аттракционы и тарифы на брендированных лендингах;
- оформляет бронирование в многошаговом визарде;
- управляет профилем, избранным и историей заказов;
- оставляет отзывы;
- а администратор — управляет платформой через панель `/admin`.

Frontend **не содержит бизнес-логики хранения** — он отправляет запросы на backend и отображает ответы.

### 3.2. Технологический стек

| Компонент | Технология | Зачем выбрана |
|-----------|------------|---------------|
| Framework | Next.js 14 (App Router) | SSR для SEO, файловая маршрутизация, Server/Client Components |
| UI | React 18 | Компонентная модель, виртуальный DOM |
| Язык | TypeScript 5 | Типобезопасность, автодополнение, меньше багов |
| Стили | Tailwind CSS 3.4 | Utility-first, быстрая вёрстка, адаптивность |
| Шрифты | Plus Jakarta Sans, Playfair Display | Современная типографика |
| Изображения | next/image | Оптимизация, lazy loading, responsive |
| Состояние | React hooks + localStorage | Без тяжёлых state-менеджеров для MVP |

### 3.3. Архитектура: App Router

Next.js 14 использует **файловую маршрутизацию** — каждая папка в `src/app/` = URL:

```
src/app/
├── page.tsx              → /
├── layout.tsx            → общий layout (Navbar + Footer)
├── auth/page.tsx         → /auth
├── account/page.tsx      → /account
├── admin/page.tsx        → /admin
├── parks/
│   ├── page.tsx          → /parks (каталог)
│   └── [slug]/page.tsx   → /parks/:slug (редирект на worlds)
├── checkout/
│   ├── page.tsx          → /checkout
│   ├── [slug]/page.tsx   → /checkout/:slug
│   └── star-wars/page.tsx → redirect
└── worlds/
    ├── star-wars/page.tsx
    ├── harry-potter/page.tsx
    ├── marvel/page.tsx
    └── jurassic/page.tsx
```

**Server Components** (по умолчанию) — данные загружаются на сервере при рендере страницы.  
**Client Components** (`'use client'`) — интерактивность: формы, auth, checkout, admin.

### 3.4. Структура `src/`

| Папка | Назначение |
|-------|------------|
| `app/` | Страницы и layouts (маршрутизация) |
| `components/` | Переиспользуемые UI-компоненты |
| `components/checkout/` | Многошаговые визарды оформления |
| `components/hp/, sw/, mv/, jp/` | UI-элементы вселенных |
| `lib/api.ts` | Клиент публичного REST API |
| `lib/admin-api.ts` | Клиент админ API |
| `lib/auth.ts` | Сессия, избранное, localStorage |
| `lib/config.ts` | `API_BASE = http://127.0.0.1:4000` |
| `lib/worlds.ts` | Маршрутизация парков → themed pages |
| `lib/theme-routes.ts` | Подмена Navbar/Footer по теме |

### 3.5. Интеграция с backend

**Базовый URL:** `NEXT_PUBLIC_API_URL` → `http://127.0.0.1:4000`

Все запросы идут через типизированные функции в `lib/api.ts`:

```typescript
getParks()        → GET  /api/v1/parks
getPark(slug)     → GET  /api/v1/parks/:slug
getTickets(slug)  → GET  /api/v1/parks/:slug/tickets
createBooking()   → POST /api/v1/bookings
getReviews()      → POST /api/v1/reviews
// и т.д.
```

**Особенность `safeFetch()`:** если backend недоступен, сайт не падает — показывает пустые списки и подсказку «Запустите backend». Это **graceful degradation**.

**Авторизация:** JWT хранится в `localStorage` (`parkpass_token`), передаётся в заголовке `Authorization: Bearer`.

### 3.6. Поток аутентификации (frontend)

```
Пользователь → /auth
  → форма login/register
  → POST /api/v1/auth/login
  → saveSession(token, user) в localStorage
  → redirect на ?next= (откуда пришёл) или /account
```

**Защита маршрутов (клиентская):**
- `/account` — редирект на `/auth` без токена
- `/admin` — проверка роли admin/park_manager
- Checkout при оплате — редирект на `/auth?next=/checkout/...`

### 3.7. Тематические страницы вселенных

Главная особенность frontend — **не шаблонные карточки**, а **иммерсивные брендированные лендинги**:

| Вселенная | URL | Палитра | Особенности UI |
|-----------|-----|---------|----------------|
| Star Wars | `/worlds/star-wars` | Чёрный + жёлтый `#FFE81F` | Звёздное небо, grain-эффект, StarCosmos |
| Harry Potter | `/worlds/harry-potter` | Тёмный + золото `#c9a227` | Bento-gallery, искры HpSparkles |
| Marvel | `/worlds/marvel` | Тёмный + красный `#E23636` | Частицы MvParticles, bento-grid |

**Route-aware навигация:** на themed-страницах стандартный Navbar/Footer **автоматически заменяются** на тематические (`StarWarsNavbar`, `HarryPotterFooter` и т.д.) через `theme-routes.ts`.

Данные (парк, билеты, аттракционы, отзывы) загружаются с backend **на сервере** при рендере — быстрая первая отрисовка, SEO.

### 3.8. Бронирование (Checkout)

**Многошаговый визард** (3 шага):
1. Выбор билета и даты
2. Контактные данные
3. Подтверждение и «оплата»

Для каждой вселенной — **свой визуальный стиль**, но **единая бизнес-логика** (`confirmCheckoutBooking`):
```
Выбор билета → POST /api/v1/bookings → экран успеха с QR → /account
```

Если пользователь не авторизован — редирект на `/auth?next=...` с возвратом после входа.

### 3.9. Отзывы (UI)

Компонент `ParkReviews` на каждой themed-странице:
1. Показывает одобренные отзывы (загружены server-side)
2. Кнопка «Написать отзыв» → проверка авторизации
3. Форма: рейтинг 1–5, заголовок, текст, дата визита
4. После отправки — сообщение «Отправлено на модерацию»
5. Админ одобряет в `/admin` → отзыв появляется публично

Один компонент, **5 тем оформления** (default, sw, hp, mv, jp) — принцип DRY.

### 3.10. Админ-панель (frontend)

Маршрут `/admin` → `AdminDashboard` с 4 вкладками:

| Вкладка | Функции |
|---------|---------|
| **Обзор** | KPI: брони, выручка, пользователи, парки; последние заказы |
| **Бронирования** | Таблица, смена статуса (pending → paid → completed) |
| **Отзывы** | Фильтры, одобрение/скрытие, верификация, удаление |
| **Пользователи** | Список, смена ролей (только для admin) |

RBAC на frontend: вкладка «Пользователи» скрыта для `park_manager`.

### 3.11. Избранное (гибридная модель)

- **Без авторизации:** localStorage (`parkpass_favorites`)
- **После входа:** синхронизация с `POST/DELETE /api/v1/favorites`
- UX: мгновенный отклик локально, API — best effort

### 3.12. Что сказать на защите про frontend (готовый текст)

> Клиентская часть ParkPass построена на Next.js 14 с App Router. Мы использовали разделение на Server Components для загрузки данных с API при рендере страницы и Client Components для интерактивных элементов — форм, checkout и админ-панели.
>
> Ключевая продуктовая особенность — **тематические лендинги четырёх кино-вселенных**. Это не просто карточки в каталоге, а самостоятельные иммерсивные страницы с уникальной цветовой палитрой, анимациями и брендированной навигацией. При этом все они работают с единым REST API и общими компонентами — принцип DRY.
>
> Интеграция с backend реализована через типизированный API-слой в `lib/api.ts`. При недоступности сервера сайт не падает — срабатывает graceful degradation. Аутентификация через JWT в localStorage с редиректом `?next=` обеспечивает бесшовный UX при бронировании.
>
> Админ-панель на frontend отображает данные из `/api/v1/admin` и позволяет модерировать отзывы, управлять бронированиями и ролями пользователей — полный цикл управления платформой без прямого доступа к БД.

## 5. Возможные вопросы комиссии и ответы

### Общие

**В: В чём актуальность работы?**  
О: Туристы тратят часы на поиск билетов в разрозненных системах. ParkPass объединяет каталог, бронирование, отзывы и лояльность в одном интерфейсе.

**В: Чем ваш проект отличается от Booking.com / TripAdvisor?**  
О: Мы фокусируемся на **тематических парках развлечений** с иммерсивным брендированным UX для конкретных вселенных, а не на универсальном агрегаторе отелей.

**В: Какие требования вы реализовали?**  
О: Full-stack приложение: REST API, БД, аутентификация, CRUD, админ-панель, тесты, тематический UI.

### Backend

**В: Почему Express, а не NestJS / FastAPI?**  
О: Express — минималистичный, прозрачный, позволяет показать понимание HTTP без «магии» фреймворка. Для дипломного MVP это оптимально.

**В: Как защищены пароли?**  
О: bcrypt с cost factor 10. Пароли никогда не хранятся в открытом виде.

**В: Что такое JWT и почему не сессии?**  
О: JWT — stateless-токен. Сервер не хранит сессии, масштабируется проще. Срок — 7 дней.

**В: Зачем mock-режим?**  
О: Разработка и CI без Docker. Бизнес-логика не зависит от хранилища — демонстрирует правильное разделение слоёв.

**В: Как работает модерация отзывов?**  
О: Новый отзыв создаётся с `is_approved = false`. Публичный GET возвращает только одобренные. Админ меняет флаг через PATCH.

### Frontend

**В: Почему Next.js, а не чистый React (CRA/Vite)?**  
О: SSR для SEO лендингов, App Router, Server Components — меньше JS на клиенте, быстрее первая отрисовка.

**В: Где хранится токен? Безопасно ли в localStorage?**  
О: localStorage — стандарт для SPA/MVP. Для production рекомендуется httpOnly cookie, но для диплома JWT в localStorage достаточен с CORS-ограничением.

**В: Как реализованы тематические страницы?**  
О: Отдельные route, CSS-файлы, Navbar/Footer per theme. Данные — с единого API. Один компонент отзывов — 5 тем оформления.

**В: Что если backend недоступен?**  
О: `safeFetch()` — graceful degradation. Сайт работает, показывает пустые списки и подсказку.

### Про AI

**В: Вы использовали нейросеть при написании работы?**  
О: Да, AI-ассистенты (Cursor) использовались как инструмент ускорения. Архитектура, логика и дизайн — наши. Код проверен тестами и вручную.

**В: Это не означает, что вы не разбираетесь в коде?**  
О: Мы можем объяснить любой модуль. Демонстрация live и ответы на вопросы это подтверждают. AI — как калькулятор для математика: инструмент, а не замена знаний.
