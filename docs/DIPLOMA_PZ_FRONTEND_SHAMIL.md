## ВВЕДЕНИЕ

В современной индустрии развлечений и туризма потребление услуг тематических парков смещается в сторону онлайн-сервисов, предоставляющих не только приобретение билетов, но и инструменты поиска парков, сравнения тарифов, чтения отзывов и оформления бронирования. Тематические парки вселенных Star Wars, Harry Potter, Marvel и Jurassic World обладают обширной и устойчиво растущей аудиторией в Республике Казахстан и в мире, однако значительная часть существующих ресурсов либо ориентирована на официальные сайты отдельных операторов с разрозненным дизайном, либо не предоставляет пользователю единого каталога, тематического опыта и управления заказами. Это определяет актуальность создания собственной веб-платформы, объединяющей каталог парков, бронирование, личный кабинет, модерацию отзывов и администрирование в едином продукте.

Разрабатываемый продукт — веб-платформа агрегированного бронирования тематических парков **«ParkPass»** — представляет собой клиент-серверное веб-приложение, состоящее из двух взаимосвязанных частей: серверной части (backend), отвечающей за хранение и обработку данных, бизнес-логику, аутентификацию, авторизацию и предоставление программного интерфейса (REST API), и клиентской части (frontend), отвечающей за пользовательский интерфейс, отображение данных и взаимодействие с пользователем. Ввиду объёма и сложности продукт реализуется коллективом из двух дипломников с разделением ответственности: серверная часть и программный интерфейс разрабатываются в рамках смежного дипломного проекта (дипломник Нурғали Дархан Мырзағалиұлы), клиентская часть — в рамках настоящего дипломного проекта (дипломник Шарипов Шамиль). Настоящее введение является общим для обоих проектов и описывает платформу «ParkPass» как единое целое; последующие разделы пояснительной записки раскрывают вклад автора в клиентскую часть.

Актуальность темы обусловлена ростом внутреннего и международного туризма, отсутствием на локальном рынке удобных русскоязычных агрегаторов бронирования тематических парков с иммерсивным интерфейсом и единым checkout, а также практической потребностью отработать полный цикл проектирования и разработки полнофункционального клиент-серверного веб-приложения с применением современного технологического стека.

Объектом проектирования являются процессы поиска, сравнения и онлайн-бронирования билетов в тематические парки развлечений.

Предметом проектирования являются архитектура, структура компонентов и программные средства клиентской части платформы «ParkPass», обеспечивающие отображение каталога парков, тематических лендингов, оформление бронирований, личный кабинет, избранное, отзывы и административную панель.

Цель дипломного проекта — спроектировать и разработать клиентскую часть (frontend) веб-платформы «ParkPass», обеспечивающую каталог парков с фильтрацией, тематические лендинги четырёх кино-вселенных, многошаговое оформление бронирования, личный кабинет, избранное, отзывы, административную панель и интеграцию с REST API серверной части.

Для достижения поставленной цели определены следующие общие задачи проекта:

1) проанализировать предметную область, целевую аудиторию, существующие аналоги и выявить их недостатки;
2) сформулировать функциональные и нефункциональные требования к платформе;
3) спроектировать общую архитектуру клиент-серверного решения, модель взаимодействия компонентов и контракт REST API;
4) реализовать ключевые пользовательские сценарии и проверить их работоспособность;
5) обеспечить адаптивный пользовательский интерфейс с тематическим брендированием парков;
6) подготовить проектную документацию, экономическое обоснование и раздел по охране труда и безопасности эксплуатации.

В части клиентской разработки (вклад автора настоящего проекта) решаются следующие задачи:

1) спроектировать архитектуру клиентского приложения на Next.js 14 с разделением Server Components и Client Components;
2) реализовать глобальный макет, навигацию, каталог парков, поиск и фильтрацию с интеграцией REST API;
3) разработать тематические лендинги четырёх вселенных: Star Wars, Harry Potter, Marvel и Jurassic World;
4) реализовать многошаговый checkout с тематическим оформлением для каждой вселенной;
5) реализовать аутентификацию (JWT), личный кабинет, избранное, отзывы и административную панель;
6) обеспечить типобезопасную интеграцию с API, обработку ошибок при недоступности backend и адаптивную вёрстку на Tailwind CSS.

Серверная часть (смежный проект) включает разработку REST API на Express и TypeScript, реляционную базу данных PostgreSQL, JWT-аутентификацию, бизнес-логику бронирований и администрирования, а также интеграцию с клиентской частью.

Методы выполнения проекта: анализ предметной области и аналогов, компонентное проектирование интерфейсов, проектирование взаимодействия с REST API, итеративная разработка с использованием системы контроля версий Git, функциональное тестирование по сценариям.

Практическая значимость заключается в том, что результатом проекта является работоспособная клиентская часть платформы, которая может использоваться как пользовательский интерфейс агрегатора бронирования парков, а также как типовой шаблон построения frontend-приложения с тематическим UI, интеграцией с REST API и административной панелью.

Проектным результатом является реализованная клиентская часть платформы «ParkPass»: приложение на Next.js 14, каталог парков, четыре themed-лендинга, checkout-визарды, личный кабинет, избранное, отзывы, административная панель, типизированный API-клиент и аутентификация на стороне клиента, а также комплект документации, инструкций запуска и доказательств работоспособности (исходный код, скриншоты интерфейса, протокол функционального тестирования).

Пояснительная записка состоит из пяти разделов: аналитико-постановочной части, проектной части, практической реализации и оценки результатов, экономической части, а также раздела по охране труда, технике безопасности и безопасности эксплуатации, и завершается заключением, списком использованных источников и приложениями.

## 1 АНАЛИТИКО-ПОСТАНОВОЧНАЯ ЧАСТЬ

### 1.1 Характеристика предметной области

Предметной областью дипломного проекта является сфера **пользовательских интерфейсов онлайн-сервисов бронирования тематических парков развлечений**. Современные платформы в данной области представляют собой не просто формы заказа билетов, а информационные системы с богатым UI: структурированный каталог парков, средства поиска и фильтрации, детальные страницы аттракционов и тарифов, многошаговое оформление заказа, личный кабинет, избранное, отзывы и административные панели. Ключевую роль в восприятии продукта пользователем играет клиентская часть, обеспечивающая удобство навигации, визуальную привлекательность, адаптивность и отзывчивость интерфейса.

В рамках предметной области выделяются следующие основные пользовательские процессы на стороне frontend: просмотр каталога и themed-лендингов; поиск и фильтрация парков; изучение аттракционов, тарифов и отзывов; оформление бронирования через checkout-визард; регистрация и вход; управление профилем и историей заказов; работа с избранным; написание отзывов; администрирование (для ролей admin и park_manager). Входными данными для клиентской части являются ответы REST API; выходными — отображаемый интерфейс и действия пользователя, передаваемые на сервер.

Объектом автоматизации с точки зрения frontend является деятельность пользователя по поиску, сравнению и бронированию билетов в тематические парки через веб-интерфейс. Платформа реализуется как клиент-серверное веб-приложение: клиентская часть (frontend) отвечает за пользовательский интерфейс и взаимодействие с пользователем, серверная часть (backend) — за данные и бизнес-логику. Проект выполняется двумя дипломниками с разделением ответственности; настоящий раздел описывает платформу «ParkPass» с акцентом на клиентскую часть.

Платформа «ParkPass» включает четыре иммерсивных тематических лендинга:

| Вселенная | Маршрут | Палитра | UI-эффекты |
|-----------|---------|---------|------------|
| Star Wars | `/worlds/star-wars` | Чёрный + `#FFE81F` | StarCosmos, grain-эффект |
| Harry Potter | `/worlds/harry-potter` | Тёмный + `#c9a227` | HpSparkles, bento-gallery |
| Marvel | `/worlds/marvel` | Тёмный + `#E23636` | MvParticles, bento-grid |
| Jurassic World | `/worlds/jurassic` | Тёмный + изумруд | JpParticles, природная тема |

Помимо themed-страниц, клиентская часть включает: каталог `/parks`; многошаговый checkout `/checkout/*`; авторизацию `/auth`; личный кабинет `/account`; избранное `/favorites`; админ-панель `/admin`. На themed-маршрутах стандартные Navbar и Footer автоматически заменяются брендированными компонентами.

Таким образом, предметная область frontend охватывает как классические функции каталога и бронирования, так и требования к иммерсивному UX в сегменте развлекательного туризма, что формирует требования к компонентной, масштабируемой и сопровождаемой клиентской архитектуре.

### 1.2 Анализ существующих решений

Рынок онлайн-бронирования развлечений представлен универсальными агрегаторами (Booking.com, Klook, TripAdvisor) и официальными сайтами парков (Disney, Universal Studios). Сравнительный анализ с проектируемой платформой «ParkPass» по критериям, значимым для frontend, приведён в таблице 1.1.

**Таблица 1.1 — Сравнительный анализ существующих решений (критерии UI/UX)**

| Критерий | Универсальные агрегаторы | Официальные сайты парков | «ParkPass» |
|----------|--------------------------|--------------------------|------------|
| Единый интерфейс сравнения парков | Да | Нет | Да |
| Иммерсивный тематический UX | Нет | Да (один парк) | Да (4 вселенные) |
| Адаптивный современный UI | Средний | Разный | Высокий (Tailwind, SSR) |
| Многошаговый checkout | Да | Да | Да, с тематическим оформлением |
| Личный кабинет и избранное | Частично | Только свой парк | Да |
| Админ-панель в едином стиле | Нет | Закрытая | Да |

Проведённый анализ показывает, что универсальные агрегаторы не обеспечивают иммерсивный брендированный опыт для тематических парков, а официальные сайты не объединяют несколько вселенных в едином интерфейсе. Существует ниша для frontend с современным стеком (Next.js, SSR), themed-лендингами, единым checkout и админ-панелью — что определяет направление настоящего проекта.

### 1.4 Требования к программному продукту

Требования к клиентской части разделяются на функциональные и нефункциональные. Функциональные требования приведены в таблице 1.4.

**Таблица 1.4 — Функциональные требования к клиентской части**

| № | Группа требований | Содержание требования |
|---|-------------------|----------------------|
| 1 | Главная и навигация | Hero-секция, поиск, Navbar, Footer, route-aware themed-навигация |
| 2 | Каталог | Список парков, фильтры (category, city, brand), карточки `ParkCard` |
| 3 | Themed UI | 4 иммерсивных лендинга с уникальной палитрой и анимациями |

### 2.1 Теоретические и технологические основы выбранного направления разработки

Проектируемое решение относится к направлению разработки **клиентской части (frontend)** клиент-серверных веб-приложений. Для обоснования принятых проектных решений необходимо опираться на: компонентный подход; модели рендеринга в Next.js; архитектурный стиль REST для взаимодействия с сервером; механизмы управления состоянием на стороне клиента.

**Компонентный подход.** Современные пользовательские интерфейсы строятся из независимых, переиспользуемых компонентов. React реализует компонентную модель через функциональные компоненты и хуки (`useState`, `useEffect`), обеспечивая предсказуемое обновление интерфейса посредством виртуального DOM.

**Модели рендеринга.** Next.js 14 предоставляет несколько стратегий: серверный рендеринг (SSR) — HTML формируется на сервере при запросе; статическая генерация (SSG); клиентский рендеринг (CSR) — для интерактивных элементов. App Router вводит React Server Components, позволяя запрашивать данные о парках и отзывах на сервере без лишних клиентских запросов.

**Управление состоянием и маршрутизация.** Сессия пользователя и избранное хранятся в `localStorage`. Маршрутизация реализована через файловую систему App Router — каждая папка в `src/app/` соответствует сегменту URL.

**Интеграция с backend.** Все запросы выполняются к `http://127.0.0.1:4000/api/v1` через функции `lib/api.ts` и `lib/admin-api.ts`. JWT передаётся в заголовке `Authorization: Bearer`.

### 2.3 Обоснование выбранного решения

Выбранное решение обосновано с учётом функциональных и нефункциональных требований, сформулированных в разделе 1.4, ограничений учебного проекта, современности технологического стека и необходимости уложиться в сроки дипломного проектирования при сохранении полноценного пользовательского опыта.

**Соответствие требованиям.** Next.js 14 с App Router предоставляет все инструменты, необходимые для реализации платформы «ParkPass»: Server Components обеспечивают быструю первичную загрузку каталога парков (`/parks`), карточек и themed-лендингов (`/worlds/*`) с минимальным объёмом JavaScript на клиенте; Client Components используются для интерактивных сценариев — многошагового checkout, форм авторизации, избранного, компонента отзывов и административной панели. Встроенные средства Next.js (`next/image`, оптимизация шрифтов, code splitting) повышают производительность и качество отображения медиаконтента на themed-страницах. TypeScript обеспечивает статическую проверку типов при работе с REST API и снижает риск ошибок при интеграции с backend. Tailwind CSS позволяет реализовать адаптивную вёрстку и изолированные тематические стили (`star-wars.css`, `harry-potter.css`, `marvel.css`, `jurassic.css`) без дублирования базовой разметки. Функция `safeFetch()` в `lib/api.ts` реализует graceful degradation: при недоступности сервера интерфейс остаётся работоспособным за счёт fallback-данных, что соответствует нефункциональному требованию отказоустойчивости клиентской части.

**Стоимость и ограничения.** Все компоненты выбранного стека (Next.js 14, React 18, TypeScript, Tailwind CSS) распространяются с открытым исходным кодом на свободных лицензиях (MIT и аналогичные). Это полностью соответствует ограниченному бюджету учебного проекта и исключает затраты на коммерческие лицензии UI-библиотек и среды разработки. Развёртывание frontend возможно на бесплатном тарифе Vercel для демонстрации или на арендуемом VPS без дополнительных лицензионных платежей. Ограничением является зависимость клиентской части от доступности REST API серверной части (дипломник Нурғали Д.М.): при отсутствии backend часть функций переходит в режим деградации, однако просмотр каталога и themed-лендингов сохраняется. Проект реализуется в учебной среде без промышленной нагрузки, что допускает использование локального хранилища JWT в `localStorage` вместо более сложных схем управления сессией.

**Сопровождение и масштабируемость.** Модульная организация кода в каталогах `src/app/`, `src/components/`, `src/lib/` упрощает сопровождение и расширение функциональности. Принцип DRY реализован в переиспользуемых модулях: компонент `ParkReviews` поддерживает тематическое оформление для разных парков через параметр темы; базовый `CheckoutWizard` объединяет общую логику шагов бронирования, а специализированные визарды (`HarryPotterCheckoutWizard`, `MarvelCheckoutWizard`, `JurassicCheckoutWizard`) наследуют поведение с уникальным UI. Модуль `theme-routes.ts` и `checkout-themes.ts` централизуют маршруты и стили themed-страниц, что упрощает добавление пятой вселенной без переработки глобального макета. Разделение на Server и Client Components делает архитектуру предсказуемой: новые страницы добавляются через файловую маршрутизацию App Router без изменения конфигурации маршрутов. Административная панель `AdminDashboard` изолирована в отдельном модуле с собственным API-клиентом (`admin-api.ts`), что облегчает развитие ролевой модели на стороне UI. При росте сложности состояния приложения возможен поэтапный переход на React Context или Zustand без смены основного фреймворка.

Таким образом, выбранное решение представляет обоснованный компромисс между современностью стека, скоростью разработки, богатством экосистемы React/Next.js, возможностью реализации иммерсивного тематического интерфейса для четырёх кино-вселенных и нулевыми затратами на программные лицензии.

**Группа layout (глобальный макет).** Компоненты `Navbar` и `Footer` образуют единую оболочку приложения. `Navbar` реализует паттерн *route-aware delegation*: при монтировании считывает текущий `pathname` через хук `usePathname()` и функции из `lib/theme-routes.ts`; если маршрут относится к одной из четырёх вселенных (Star Wars, Harry Potter, Marvel, Jurassic World), рендерится соответствующий themed-navbar, иначе — `DefaultNavbar` с логотипом ParkPass, ссылками на каталог и избранное, а также блоком авторизации (аватар, имя, кнопка «Выйти» или ссылка «Войти»). Аналогичная подмена выполняется в `Footer`. Компонент `SearchBar` обеспечивает поиск парков на главной странице с переходом на `/parks` с query-параметрами. `BookingBar` — компактная панель призыва к действию с кнопкой перехода к бронированию, используемая на themed-лендингах.

**Группа themed (брендированный UI вселенных).** Для каждой кино-вселенной создана пара Navbar/Footer с уникальной цветовой палитрой, типографикой и навигационными ссылками, соответствующими контексту парка. Star Wars использует жёлтый акцент `#FFE81F` на тёмном фоне; Harry Potter — золотистый `#c9a227`; Marvel — красный `#E23636`; Jurassic World — изумрудно-зелёную гамму. Подпапки `hp/`, `sw/`, `mv/`, `jp/` содержат вспомогательные layout-компоненты (`HpLayout`, `SwLayout`) и декоративные разделители секций (`HpSparkleDivider`, `MvDivider`, `JpDivider`), которые инкапсулируют повторяющуюся разметку themed-страниц и снижают дублирование в файлах маршрутов `src/app/worlds/*/page.tsx`.

**Группа checkout (оформление заказа).** Базовый `CheckoutWizard` реализует единую бизнес-логику трёхшагового визарда: (1) выбор даты, количества гостей и типа билета; (2) ввод контактных данных и подтверждение состава заказа; (3) имитация оплаты и отображение QR-кода подтверждения. Визард принимает проп `theme` типа `CheckoutTheme` из `lib/checkout-themes.ts` и динамически подключает themed-обёртки (`StarCosmos`, `HpCosmos`, `SwContainer`, `HpContainer`). Специализированные визарды (`HarryPotterCheckoutWizard`, `MarvelCheckoutWizard`, `JurassicCheckoutWizard`) являются тонкими обёртками над базовым компонентом, передавая фиксированную тему и маршрут возврата. При попытке оформить заказ без авторизации выполняется редирект на `/auth?next=...` с сохранением контекста checkout.

**Группа content (контент и администрирование).** `ParkCard` — Server Component для отображения карточки парка в каталоге: обложка (`next/image`), название, локация, рейтинг, цена от; ссылка формируется через `getParkPageHref()` из `lib/worlds.ts` (ведёт на themed-лендинг или `/parks/[slug]`). `ParkReviews` — Client Component с поддержкой пяти тем оформления (`default`, `sw`, `hp`, `mv`, `jp`): отображает список одобренных отзывов, форму добавления отзыва (рейтинг 1–5, текст), проверку JWT-токена и сообщение о модерации. `FavoriteButton` управляет добавлением парка в избранное через `localStorage` (`lib/auth.ts`) с мгновенным обновлением состояния кнопки. `AdminDashboard` — монолитный Client Component административной панели с четырьмя вкладками: обзор (KPI-статистика), бронирования (смена статуса), отзывы (одобрение/удаление), пользователи (смена роли); данные загружаются через `lib/admin-api.ts` с проверкой роли текущего пользователя.

**Группа effects (визуальные эффекты).** Компоненты `StarCosmos` и `HpCosmos` создают анимированный звёздный/магический фон для страниц Star Wars и Harry Potter соответственно. `HpSparkles`, `MvParticles` и `JpParticles` генерируют частицы и световые акценты средствами CSS и Canvas без подключения тяжёлых библиотек анимации, что соответствует принципу минимизации зависимостей, принятому в таблице 2.1. Эффекты подключаются изолированно на themed-страницах и не влияют на производительность глобального макета.

### 5.1 Организация безопасного рабочего места разработчика

Рабочее место разработчика программного обеспечения должно соответствовать требованиям СанПиН 2.2.2/2.4.1340-03 «Гигиенические требования к персональным электронно-вычислительным машинам и организации работы». Площадь на одно рабочее место с персональным компьютером должна составлять не менее 6 кв. м, а объём — не менее 20 куб. м.

Рабочий стол должен иметь высоту 680–800 мм и достаточное пространство для размещения монитора, клавиатуры и документов. Рабочее кресло должно обеспечивать поддержание рациональной рабочей позы, регулировку высоты сиденья в диапазоне 400–550 мм, наклон спинки и подлокотники.

Монитор должен располагаться на расстоянии 600–700 мм от глаз пользователя на уровне или чуть ниже линии взора. Освещённость рабочей поверхности стола должна составлять 300–500 лк. Для снижения бликов на экране рекомендуется использовать жалюзи или шторы на окнах. При разработке клиентской части платформы «ParkPass», предполагающей длительную работу с визуальным оформлением themed-страниц, цветовыми палитрами и адаптивной вёрсткой, особое значение имеет качество монитора (достаточная диагональ, разрешение, отсутствие мерцания) и равномерное освещение рабочей зоны.

Температура воздуха в рабочем помещении должна быть в диапазоне 22–24 °C в тёплый период и 21–23 °C в холодный. Относительная влажность воздуха — 40–60 %, уровень шума — не более 50 дБА. Необходимо обеспечить регулярное проветривание помещения или наличие кондиционирования воздуха. Основные требования к организации рабочего места разработчика приведены на рисунке 5.1.

### 5.2 Требования электробезопасности

Разработчик программного обеспечения работает с электрическим оборудованием, поэтому соблюдение правил электробезопасности является обязательным. Помещения с компьютерной техникой относятся к категории помещений без повышенной опасности при выполнении всех нормативных требований.

Все электрические приборы должны быть заземлены в соответствии с ПУЭ (Правила устройства электроустановок). Электрические розетки должны иметь защитный контакт заземления. Сопротивление изоляции электропроводки должно проверяться не реже одного раза в три года.

Запрещается: самостоятельно ремонтировать компьютер и периферийные устройства, находящиеся под напряжением; эксплуатировать оборудование с повреждённой изоляцией кабелей; оставлять без присмотра включённое оборудование; допускать перегрузку электрических сетей путём подключения нескольких потребителей через тройники без защитных выключателей. При одновременной работе системного блока, монитора, периферии и зарядных устройств мобильных устройств необходимо использовать сетевой фильтр с защитой от перегрузки.

При обнаружении неисправности электрооборудования необходимо немедленно отключить его от сети и сообщить ответственному за электробезопасность или руководителю. До устранения неисправности эксплуатация оборудования запрещена. Основные требования электробезопасности представлены на рисунке 5.2.

### 5.3 Пожарная безопасность

Помещения с вычислительной техникой относятся к категории В по взрывопожарной и пожарной опасности (пожароопасные). Основными источниками возгорания могут являться неисправная электропроводка, перегрев компьютерных компонентов, короткое замыкание, а также несоблюдение правил пожарной безопасности.

В помещении должны быть установлены автоматические датчики дымовой сигнализации и огнетушители типа ОУ-2 или ОУ-5 (углекислотные), пригодные для тушения электрооборудования. Применение пенных или водных огнетушителей для тушения электрооборудования под напряжением категорически запрещено.

В целях пожарной безопасности запрещается: хранить в помещении легковоспламеняющиеся вещества; загромождать проходы и пути эвакуации; пользоваться самодельными электроприборами; оставлять без присмотра работающее оборудование по окончании рабочего дня. Все сотрудники должны знать план эвакуации и расположение первичных средств пожаротушения.

При обнаружении пожара или задымления необходимо немедленно сообщить в пожарную службу по номеру 101, оповестить присутствующих и покинуть помещение по пути эвакуации, не пользуясь лифтом. Приступать к тушению очага пожара первичными средствами допускается только при отсутствии угрозы жизни и здоровью. Средства пожаротушения и категория помещения показаны на рисунке 5.3.

### 5.4 Меры по снижению утомляемости при работе за компьютером

Длительная работа за компьютером оказывает негативное воздействие на органы зрения, опорно-двигательный аппарат и нервную систему. Для снижения утомляемости необходимо соблюдать режим труда и отдыха, установленный СанПиН: при 8-часовом рабочем дне суммарное время непосредственной работы с компьютером не должно превышать 6 часов.

Регламентированные перерывы в работе необходимо устраивать через каждые 45–60 минут непрерывной работы с компьютером продолжительностью 10–15 минут. Во время перерывов рекомендуется выполнять комплекс упражнений для глаз, шеи, рук и спины, а также проводить время вдали от экрана.

Для снижения нагрузки на зрение рекомендуется использовать мониторы с антибликовым покрытием, устанавливать оптимальную яркость и контрастность изображения. Применение правила «20-20-20» — каждые 20 минут смотреть на объект, удалённый на 20 футов (~6 м), в течение 20 секунд — существенно снижает напряжение глазных мышц. export async function safeFetch(input: string, init?: RequestInit): Promise<Response | null> {
```typescript
  try {
    return await fetch(input, init);
  } catch {
    return null;
  }
}

export async function getParks(params?: { category?: string; city?: string }): Promise<Park[]> {
  const q = new URLSearchParams();
  if (params?.category) q.set('category', params.category);
  const res = await safeFetch(`${API}/api/v1/parks?${q}`, { cache: 'no-store' });
  if (!res?.ok) return [];
  const json = await res.json();
  return json.data ?? [];
}
```
