## ВВЕДЕНИЕ

В современной индустрии развлечений тематические парки — один из наиболее динамично развивающихся сегментов туризма. Поездка в парки вселенных Star Wars, Harry Potter, Marvel и Jurassic World требует предварительного планирования: выбора даты, сравнения тарифов, изучения аттракционов и чтения отзывов. При этом официальные сайты парков разрознены, используют разные валюты и интерфейсы, не предоставляют единого каталога и инструментов сравнения. Турист вынужден открывать десятки вкладок, что увеличивает время планирования и риск ошибки при выборе билета.

Разрабатываемый продукт — веб-платформа **«ParkPass»** («ваш пропуск в мир приключений») — представляет собой клиент-серверное веб-приложение, состоящее из двух взаимосвязанных частей: **серверной части (backend)**, отвечающей за хранение и обработку данных, бизнес-логику бронирования, аутентификацию, авторизацию и предоставление REST API, и **клиентской части (frontend)**, отвечающей за пользовательский интерфейс, тематические лендинги парков, оформление заказов и взаимодействие с пользователем.

Ввиду объёма и сложности продукт реализуется коллективом из двух дипломников с разделением ответственности: **серверная часть и программный интерфейс** разрабатываются в рамках дипломного проекта дипломника **Нурғали Дархана Мырзағалиұлы**; **клиентская часть** — в рамках дипломного проекта дипломника **Шарипова Шамиля**. Настоящее введение является общим для обоих проектов и описывает платформу «ParkPass» как единое целое; последующие разделы раскрывают вклад каждого автора в соответствующую часть системы.

**Актуальность** темы обусловлена ростом внутреннего и международного туризма в Республике Казахстан, отсутствием на локальном рынке удобных русскоязычных агрегаторов бронирования тематических парков с единым интерфейсом, системой лояльности и модерацией отзывов, а также практической потребностью отработать полный цикл проектирования и разработки полнофункционального клиент-серверного веб-приложения с применением современного технологического стека.

**Объектом проектирования** являются процессы поиска, сравнения и онлайн-бронирования билетов в тематические парки развлечений.

**Предметом проектирования** являются архитектура, модель данных и программные средства веб-платформы «ParkPass», обеспечивающие управление каталогом парков, бронированиями, пользователями, отзывами, избранным и администрирование системы.

**Цель дипломного проекта** — спроектировать и разработать веб-платформу «ParkPass» для агрегированного бронирования билетов в тематические парки, обеспечивающую каталог парков с фильтрацией, оформление бронирований с QR-подтверждением, систему лояльности, модерацию отзывов, ролевую модель доступа и документированный REST API для клиентской части.

Для достижения поставленной цели определены следующие **общие задачи проекта**:

1) проанализировать предметную область, целевую аудиторию, существующие аналоги и выявить их недостатки;
2) сформулировать функциональные и нефункциональные требования к платформе;
3) спроектировать общую архитектуру клиент-серверного решения, модель данных и контракт REST API;
4) реализовать ключевые пользовательские сценарии и проверить их работоспособность;
5) обеспечить адаптивный пользовательский интерфейс с тематическим брендированием парков;
6) подготовить проектную документацию, экономическое обоснование и раздел по охране труда и безопасности эксплуатации.

**В части серверной разработки** (вклад автора Нурғали Д.М.) решаются следующие задачи:

1) спроектировать и реализовать реляционную базу данных платформы (пользователи, парки, аттракционы, типы билетов, бронирования, отзывы, избранное, роли);
2) реализовать серверную бизнес-логику на Node.js и Express с предоставлением REST API версии 2.1;
3) реализовать аутентификацию и авторизацию на основе JWT с разграничением прав по ролям (user, park_manager, admin);
4) реализовать сервисы бронирования, расписания, доступности слотов, отзывов и администрирования;
5) обеспечить dual-mode работу: PostgreSQL для production-демонстрации и in-memory mock для разработки и автотестов;
6) организовать автоматизированное тестирование API (Jest + Supertest).

**Клиентская часть** (вклад автора Шарипова Ш.) включает разработку пользовательского интерфейса на Next.js 14 и React 18, реализацию каталога парков, иммерсивных тематических лендингов четырёх вселенных (Star Wars, Harry Potter, Marvel, Jurassic World), многошагового checkout, личного кабинета, избранного, отзывов и административной панели, а также интеграцию с REST API серверной части.

**Методы выполнения проекта:** анализ предметной области и аналогов, объектно-ориентированное проектирование, проектирование реляционной модели данных, проектирование REST API, итеративная разработка с использованием системы контроля версий Git, функциональное и интеграционное тестирование по сценариям.

**Практическая значимость** заключается в том, что результатом проекта является работоспособная клиент-серверная платформа, которая может использоваться как MVP реального агрегатора бронирования парков, а также как типовой шаблон построения full-stack веб-приложения с разделением на backend и frontend, ролевой моделью, модерацией пользовательского контента и тематическим UI.

**Проектным результатом** является реализованная платформа «ParkPass»: база данных PostgreSQL 16 (7 таблиц), серверное приложение на Express 4 и TypeScript, документированный REST API (30+ эндпоинтов), клиентское приложение на Next.js 14 с тематическими страницами, механизмы аутентификации и авторизации, административная панель, 13 интеграционных автотестов backend, а также комплект документации, инструкций запуска и доказательств работоспособности.

Пояснительная записка состоит из пяти разделов: аналитико-постановочной части, проектной части, практической реализации и оценки результатов, экономической части, а также раздела по охране труда, технике безопасности и безопасности эксплуатации, и завершается заключением, списком использованных источников и приложениями.

## 1 АНАЛИТИКО-ПОСТАНОВОЧНАЯ ЧАСТЬ

### 1.1 Характеристика предметной области

Предметной областью дипломного проекта является сфера **онлайн-бронирования и агрегирования услуг тематических парков развлечений**. Современные платформы в данной области представляют собой не просто витрины билетов, а информационные системы, объединяющие структурированный каталог парков и аттракционов, средства поиска и фильтрации, сравнение тарифов, оформление бронирований, учёт истории заказов, персональную систему лояльности, отзывы туристов и административные инструменты для операторов.

В рамках предметной области выделяются следующие основные процессы: ведение каталога парков, аттракционов и типов билетов; регистрация и аутентификация пользователей; проверка доступности слотов на выбранную дату; создание и ведение бронирований с генерацией QR-кода; формирование системы лояльности (баллы, уровни клуба); взаимодействие пользователей с контентом (отзывы, избранное); администрирование бронирований, отзывов и учётных записей.

Входными данными системы являются сведения о парках, аттракционах и тарифах, действия пользователей и их учётные данные; выходными — отображаемый каталог, подтверждения бронирований, агрегированная статистика для администраторов, ответы программного интерфейса.

**Объектом автоматизации** является деятельность онлайн-платформы по предоставлению пользователям каталога тематических парков, инструментов сравнения и бронирования билетов, личного кабинета и социальных функций (отзывы, избранное). Платформа реализуется как клиент-серверное веб-приложение: серверная часть обеспечивает хранение данных, бизнес-логику, безопасность и программный интерфейс, а клиентская часть — пользовательский интерфейс и взаимодействие с пользователем.

Платформа «ParkPass» ориентирована на четыре тематические вселенные:

| Вселенная | Парк в каталоге | Город |
|-----------|-----------------|-------|
| Star Wars | Star Wars: Galaxy's Edge | Orlando & Anaheim |
| Harry Potter | The Wizarding World of Harry Potter | Orlando |
| Marvel | Avengers Campus | California |
| Jurassic World | Jurassic World — Islands of Adventure | Orlando |

Помимо базовых функций агрегатора, платформа включает **иммерсивные тематические лендинги** с уникальной цветовой палитрой, анимациями и брендированной навигацией для каждой вселенной; **многошаговый checkout** с тематическим оформлением; **систему клубных уровней** (Bronze → Platinum); **модерацию отзывов** перед публикацией; **административную панель** с KPI, отчётами и управлением ролями.

Таким образом, предметная область охватывает как классические функции каталога и бронирования, так и требования к качественному UX в сегменте развлекательного туризма, что формирует требования к масштабируемой, безопасной и сопровождаемой архитектуре.

### 1.2 Анализ существующих решений

Рынок онлайн-бронирования развлечений в международном и русскоязычном сегментах представлен двумя основными группами решений. К первой относятся **универсальные туристические агрегаторы** (Booking.com, TripAdvisor, Klook); ко второй — **официальные сайты парков** (Disney, Universal Studios, отдельные landing pages аттракционов). Сравнительный анализ типовых представителей этих групп с проектируемой платформой «ParkPass» по ключевым критериям приведён в таблице 1.1.

**Таблица 1.1 — Сравнительный анализ существующих решений**

| Критерий | Универсальные агрегаторы | Официальные сайты парков | «ParkPass» |
|----------|--------------------------|--------------------------|------------|
| Фокус на тематических парках | Частичный | Полный (один парк) | Полный (несколько вселенных) |
| Единый интерфейс сравнения | Да | Нет | Да |
| Иммерсивный тематический UX | Нет | Да (для своего парка) | Да (4 вселенные) |
| Система лояльности | Ограниченная | Только свой парк | Кросс-парковая |
| Модерация отзывов | Да | Разрозненно | Да, встроенная |
| Открытый REST API | Нет | Нет | Да |
| Клубные уровни и баллы | Редко | Редко | Да |

Проведённый анализ показывает, что универсальные агрегаторы не обеспечивают специализированный UX для тематических парков и не объединяют кино-вселенные в едином брендированном опыте, а официальные сайты парков не позволяют сравнивать предложения разных операторов в одном интерфейсе. Таким образом, существует ниша для платформы с современной full-stack архитектурой, единым каталогом, бронированием, лояльностью, модерацией отзывов и документированным REST API — что и определяет направление настоящего проекта.

## 2 ПРОЕКТНАЯ ЧАСТЬ

### 2.1 Теоретические и технологические основы выбранного направления разработки

Проектируемое решение относится к направлению разработки **full-stack клиент-серверных веб-приложений**. Для обоснования принятых решений необходимо опираться на: трёхзвенную архитектуру (Presentation → Application → Data); компонентный подход к построению интерфейсов; архитектурный стиль REST; паттерн разделения ответственности (Routes → Middleware → Services → Data).

**Трёхзвенная архитектура.** Клиент (браузер, Next.js) не имеет прямого доступа к базе данных. Все операции проходят через REST API. Сервер (Express) обрабатывает бизнес-логику и обращается к PostgreSQL. Это обеспечивает безопасность, масштабируемость и независимое развитие клиентской и серверной частей.

**Компонентный подход (frontend).** React реализует компонентную модель через функциональные компоненты и хуки (useState, useEffect), обеспечивая предсказуемое обновление интерфейса. Next.js 14 App Router вводит Server Components для загрузки данных на сервере и Client Components для интерактивности (формы, checkout, admin).

**REST API.** Взаимодействие клиент—сервер построено на ресурсах: `/parks`, `/bookings`, `/reviews`, `/admin`. Авторизация — заголовок `Authorization: Bearer <JWT>`.

**Dual-mode backend.** Сервисы проверяют доступность PostgreSQL (`dbIsReady()`) и прозрачно переключаются на in-memory mock. Это демонстрирует правильное разделение слоёв: бизнес-логика не зависит от конкретного хранилища.

### 2.3 Обоснование выбранного решения

Выбранное решение обосновано с учётом функциональных требований, ограничений учебного проекта и современности стека.

**Соответствие требованиям.** Express + PostgreSQL обеспечивают полный цикл: каталог, бронирование, отзывы, RBAC, отчёты. Next.js 14 предоставляет SSR для themed-лендингов, Client Components для checkout и admin.

**Стоимость.** Все компоненты стека распространяются с открытым исходным кодом. Docker Compose для PostgreSQL не требует платных лицензий.

**Сопровождение.** Модульная структура `routes/`, `services/`, `components/`, `lib/` упрощает расширение. Единый каталог `catalog.ts` для seed и mock исключает расхождения данных между средами.

### 3.2 Практическая разработка программного продукта

#### Серверная часть (вклад Нурғали Д.М.)

**Аутентификация.** Регистрация: валидация email/пароля → `bcrypt.hash(password, 10)` → INSERT в users → JWT `{ sub: userId, email }`, срок 7 дней. Защита эндпоинтов: `requireAuth`, `requireRole('admin', 'park_manager')`.

**Модуль парков.** GET `/parks` с фильтрами (category, city, brand, minRating, maxPrice). GET `/parks/:slug/schedule` — расписание на 7 дней. GET `/parks/:slug/availability` — проверка слотов (capacity 500 гостей/день).

**Модуль бронирований.** POST `/bookings`: parkSlug, ticketId, visitDate, guests, totalAmount → генерация QR `PP-{timestamp}` → статус `paid` → начисление баллов лояльности `floor(totalAmount)`.

**Модуль отзывов.** Новый отзыв создаётся с `is_approved = false`. Публичный GET возвращает только одобренные. При изменении пересчитывается `rating_avg` парка.

**Администрирование.** Статистика (пользователи, парки, брони, выручка), управление статусами бронирований, модерация отзывов, смена ролей (только admin), отчёты по бронированиям и посетителям. **Всего 30+ эндпоинтов.**

#### Клиентская часть (вклад Шарипова Ш.)

**Глобальный макет.** `layout.tsx` подключает Navbar, Footer, глобальные стили Tailwind. На themed-маршрутах — автозамена навигации через `theme-routes.ts`.

**Каталог `/parks`.** Server Component загружает парки с API при рендере. Фильтры по категории, городу, рейтингу. Карточки парков с ценой «от» и рейтингом.

**Themed-лендинги.** Четыре иммерсивные страницы с уникальной палитрой:

| Вселенная | Палитра | UI-эффекты |
|-----------|---------|------------|
| Star Wars | Чёрный + `#FFE81F` | StarCosmos, grain-эффект |
| Harry Potter | Тёмный + `#c9a227` | HpSparkles, bento-gallery |
| Marvel | Тёмный + `#E23636` | MvParticles, bento-grid |
| Jurassic World | Тёмный + изумруд | JpParticles, природная тема |

**Checkout.** Многошаговый визард (3 шага): выбор билета и даты → контактные данные → подтверждение. Для каждой вселенной — свой визуальный стиль (`CheckoutWizard`, `StarWarsCheckoutWizard` и др.), единая логика `confirmCheckoutBooking`.

**Интеграция с API.** Типизированный клиент `lib/api.ts`, `lib/admin-api.ts`. Функция `safeFetch()` — graceful degradation при недоступности backend.

**Отзывы.** Компонент `ParkReviews` — 5 тем оформления (default, sw, hp, mv, jp). После отправки — «Отправлено на модерацию».

**Админ-панель `/admin`.** Вкладки: Обзор (KPI), Бронирования, Отзывы, Пользователи. RBAC: вкладка «Пользователи» скрыта для park_manager.

**Избранное (гибридная модель).** Без авторизации — localStorage; после входа — синхронизация с API.

**Реализация глобального макета (frontend).** Корневой `layout.tsx` оборачивает всё приложение: подключает глобальные стили Tailwind, шрифты Plus Jakarta Sans и Playfair Display, компоненты Navbar и Footer. На themed-маршрутах (`/worlds/*`) стандартная навигация автоматически заменяется на брендированную через модуль `lib/theme-routes.ts`.

**Реализация каталога и поиска.** Страница `/parks` использует Server Component для первичной загрузки данных с API при рендере, обеспечивая быстрое появление контента. Компонент `SearchBar` на главной странице перенаправляет пользователя в каталог с параметрами поиска. Фильтрация по категории вселенной (star-wars, harry-potter, marvel, jurassic), городу, рейтингу и цене синхронизируется с запросом к `GET /api/v1/parks`.

**Система аутентификации (frontend).** JWT-токен и данные пользователя сохраняются в `localStorage` (`parkpass_token`, `parkpass_user`). **Реализация отзывов.** Компонент `ParkReviews` отображает одобренные отзывы, загруженные server-side. Форма нового отзыва: рейтинг 1–5, заголовок, текст, дата визита. После отправки пользователь видит сообщение о прохождении модерации. Один компонент поддерживает 5 тем оформления — принцип DRY.

**Админ-панель (frontend).** Компонент `AdminDashboard` на маршруте `/admin` содержит вкладки: Обзор (KPI — брони, выручка, пользователи), Бронирования (таблица со сменой статуса), Отзывы (одобрение, скрытие, верификация, удаление), Пользователи (смена ролей, только для admin). Данные загружаются через `lib/admin-api.ts`.

## 5 ОХРАНА ТРУДА И ТЕХНИКА БЕЗОПАСНОСТИ

### 5.1 Организация безопасного рабочего места разработчика

Рабочее место разработчика программного обеспечения должно соответствовать требованиям СанПиН 2.2.2/2.4.1340-03 «Гигиенические требования к персональным электронно-вычислительным машинам и организации работы». Площадь на одно рабочее место с персональным компьютером должна составлять не менее 6 кв. м, а объём — не менее 20 куб. м.

Рабочий стол должен иметь высоту 680–800 мм и достаточное пространство для размещения монитора, клавиатуры и документов. Рабочее кресло должно обеспечивать поддержание рациональной рабочей позы, регулировку высоты сиденья в диапазоне 400–550 мм, наклон спинки и подлокотники.

Монитор должен располагаться на расстоянии 600–700 мм от глаз пользователя на уровне или чуть ниже линии взора. Освещённость рабочей поверхности стола должна составлять 300–500 лк. Для снижения бликов на экране рекомендуется использовать жалюзи или шторы на окнах.

Температура воздуха в рабочем помещении должна быть в диапазоне 22–24 °C в тёплый период и 21–23 °C в холодный. Относительная влажность воздуха — 40–60 %, уровень шума — не более 50 дБА. Необходимо обеспечить регулярное проветривание помещения или наличие кондиционирования воздуха. Основные требования к организации рабочего места разработчика приведены на рисунке 5.1.

### 5.2 Требования электробезопасности

Разработчик программного обеспечения работает с электрическим оборудованием, поэтому соблюдение правил электробезопасности является обязательным. Помещения с компьютерной техникой относятся к категории помещений без повышенной опасности при выполнении всех нормативных требований.

Все электрические приборы должны быть заземлены в соответствии с ПУЭ (Правила устройства электроустановок). Электрические розетки должны иметь защитный контакт заземления. Сопротивление изоляции электропроводки должно проверяться не реже одного раза в три года.

Запрещается: самостоятельно ремонтировать компьютер и периферийные устройства, находящиеся под напряжением; эксплуатировать оборудование с повреждённой изоляцией кабелей; оставлять без присмотра включённое оборудование; допускать перегрузку электрических сетей путём подключения нескольких потребителей через тройники без защитных выключателей.

При обнаружении неисправности электрооборудования необходимо немедленно отключить его от сети и сообщить ответственному за электробезопасность или руководителю. До устранения неисправности эксплуатация оборудования запрещена. Основные требования электробезопасности представлены на рисунке 5.2.

### 5.3 Пожарная безопасность

Помещения с вычислительной техникой относятся к категории В по взрывопожарной и пожарной опасности (пожароопасные). Основными источниками возгорания могут являться неисправная электропроводка, перегрев компьютерных компонентов, короткое замыкание, а также несоблюдение правил пожарной безопасности.

В помещении должны быть установлены автоматические датчики дымовой сигнализации и огнетушители типа ОУ-2 или ОУ-5 (углекислотные), пригодные для тушения электрооборудования. Применение пенных или водных огнетушителей для тушения электрооборудования под напряжением категорически запрещено.

В целях пожарной безопасности запрещается: хранить в помещении легковоспламеняющиеся вещества; загромождать проходы и пути эвакуации; пользоваться самодельными электроприборами; оставлять без присмотра работающее оборудование по окончании рабочего дня. Все сотрудники должны знать план эвакуации и расположение первичных средств пожаротушения.

При обнаружении пожара или задымления необходимо немедленно сообщить в пожарную службу по номеру 101, оповестить присутствующих и покинуть помещение по пути эвакуации, не пользуясь лифтом. Приступать к тушению очага пожара первичными средствами допускается только при отсутствии угрозы жизни и здоровью. Средства пожаротушения и категория помещения показаны на рисунке 5.3.

### 5.4 Меры по снижению утомляемости при работе за компьютером

Длительная работа за компьютером оказывает негативное воздействие на органы зрения, опорно-двигательный аппарат и нервную систему. Для снижения утомляемости необходимо соблюдать режим труда и отдыха, установленный СанПиН: при 8-часовом рабочем дне суммарное время непосредственной работы с компьютером не должно превышать 6 часов.

Регламентированные перерывы в работе необходимо устраивать через каждые 45–60 минут непрерывной работы с компьютером продолжительностью 10–15 минут. Во время перерывов рекомендуется выполнять комплекс упражнений для глаз, шеи, рук и спины, а также проводить время вдали от экрана.

Для снижения нагрузки на зрение рекомендуется использовать мониторы с антибликовым покрытием, устанавливать оптимальную яркость и контрастность изображения. Применение правила «20-20-20» — каждые 20 минут смотреть на объект, удалённый на 20 футов (~6 м), в течение 20 секунд — существенно снижает напряжение глазных мышц.
```typescript
export function requireAuth(req: Request, res: Response, next: NextFunction) {
  const header = req.headers.authorization;
  if (!header?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Требуется авторизация' });
  }
  const token = header.slice(7);
  try {
    const payload = jwt.verify(token, JWT_SECRET) as JwtPayload;
    req.userId = payload.sub;
    next();
  } catch {
    return res.status(401).json({ error: 'Недействительный токен' });
  }
}
```
